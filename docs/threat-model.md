# Threat model and adversarial evaluation

This document states what OmniTrust Ledger defends against, what it does not, and the evidence for each claim. The capability and scenario tables are generated from `lib/security-lab/catalog.ts` and from a real run of every Security Lab scenario (`npm run lab:evaluate`). `tests/security-lab/threat-model.test.ts` fails if the catalogue and this document drift apart.

It is written for the paper's threat-model section (outline §VI). It does not claim more than the scenarios show: a scenario that held shows that one attack, as implemented, was stopped by the stated mechanism in one run. It is not a proof of security.

## System and assets

The system is one local installation (see [`README.md`](../README.md)):
- a Next.js application;
- a SQLite database;
- a directory of AES-256-GCM encrypted document blobs;
- a master key that encrypts every private key and blob;
- a local root CA, Time-Stamp Authority and audit signer;
- an optional local chain for anchoring.

The assets are:
- **document integrity:** the verified bytes are the signed bytes;
- **signature authenticity:** a signature was made with the key its certificate names;
- **algorithm binding:** a signature is judged only under its own algorithm;
- **revocation:** a compromised key's signatures stop verifying as authentic;
- **time of existence:** a trusted time-stamp is bound to the signature it dates;
- **log integrity:** security-relevant events cannot be edited, rewritten or truncated unnoticed;
- **authentication:** passwords cannot be guessed online at scale.

## Trust assumptions

1. **Cryptography.** The primitives provided by OpenSSL (through `node:crypto`), `@noble/ed25519`, `@noble/post-quantum` and `@noble/curves` are correct and their keys are generated with sufficient entropy. The Security Lab does not test this; the provider tests check known-answer vectors and cross-implementation agreement.
2. **Trust anchor.** The root CA certificate is distributed to verifiers out of band. Nothing outside this installation trusts it.
3. **Trust-service keys.** The private keys of the CA, the Time-Stamp Authority and the audit signer are not available to the adversary. They are encrypted under the master key, so an adversary who also holds the master key is the `host-compromise` capability, which is out of scope.
4. **Verifier.** The verifier runs the unmodified workflow in `lib/documents/verification.ts`.

## Verdict model

Verification returns one of four verdicts that are never merged:
- **VALID:** every required step passed.
- **INVALID:** a step found positive evidence against the signature, for example a hash mismatch, a signature that does not verify, or a key reported compromised before the trusted time.
- **UNVERIFIABLE:** evidence needed for a decision could not be obtained or authenticated, for example a CRL that does not verify.
- **ERROR:** the verifier itself failed.

The security argument therefore has two halves. An attack succeeds only if it turns a tampered or revoked signature into **VALID**. An attack that forces **UNVERIFIABLE** or **ERROR** can deny a decision but cannot forge one. The `forged-crl` scenario exercises exactly that distinction.

## What the evaluation does not show

- **One run per scenario, on one machine.** Scenarios are deterministic attacks, not sampled measurements, so a repeated run is a regression check rather than more evidence. The test suite runs every scenario on every `npm run ci`.
- **Implemented attacks only.** Each row tests the attack as written in `lib/security-lab/scenarios.ts`. A variant not written down is not covered by that row.
- **Out-of-scope capabilities are not mitigated here.** The table states their consequences.
  - The most important is `host-compromise`: an adversary holding the database, the storage and the master key together can sign, issue certificates and forge checkpoints.
  - Master-key custody (see [`README.md`](../README.md)) raises the cost of a stolen copy of the files. It does not help against a live compromise of the running host.
- **Audit-log limits.** The audit log's own limits are tested as limits in `tests/audit/checkpoints.test.ts`:
  - rewrites after the latest checkpoint are not detected;
  - deleting the newest checkpoint together with the entries it covers is not detected without an anchor.
